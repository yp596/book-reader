# 剩余难点功能 · 依赖选型调研

> 目的：为 `docs/功能总清单.md` 中剩余的高难度功能（P2/P3 为主）确定技术路线。
> 所有结论来自公开仓库源码、npm/jsDelivr 元数据与本机实测，附可追溯来源。
> **标注「未验证」的条目为置信度不足，落地前需复测。**

---

## 0. 结论速览

| 功能 | 选定方案 | 体积代价 | 风险 |
| --- | --- | --- | --- |
| PDF 编辑（合并/拆分/删页/水印/页码/表单/裁剪） | `pdf-lib` | +0.5 MB | 低。**加密不支持**，需另寻 |
| PDF 重排 | 先做「适配宽度」；文字级重排自研 | 0（阶段一） | 中。不能回写 PDF，仅阅读视图层 |
| 中文 OCR | **`RapidOCR`（PP-OCR ONNX）+ `onnxruntime-web`**（已定） | +28~35 MB | 中。需自写前后处理 |
| 本地词典 | **`js-mdict@6.x`（锁定 MIT 版本）**（已定） | +0.45 MB | 低。MDX 无全文检索 |
| 简繁转换 | `opencc-js` | +107 KiB（繁→简）/ +1.05 MB（简→繁） | 低 |
| 漫画 CBZ/CBT/CB7/CBR | 先只做 CBZ（复用 `jszip`）；再引 `libarchive.js` | +1 MB | 低 |
| 跨文档全文检索 | `sql.js` 现有 FTS4 + 中文 bigram 预处理 | 索引约 2× 原文 | 低 |

**已定决策（2026-09-10）**

1. 中文 OCR 走 **RapidOCR**（多约 30 MB，换更好的中文精度），不走 tesseract.js。
2. 词典引擎锁 **`js-mdict@6.x`**，避开 v7 起的 AGPL。

## 1. PDF 重排与编辑

### 1.1 k2pdfopt 只能借鉴算法，不能集成

k2pdfopt 是该领域最经典的实现，但有两个硬伤：

1. **许可证为 AGPL-3.0**。源码头部原文（已核验）：
   ```
   ** it under the terms of the GNU Affero General Public License as
   ** published by the Free Software Foundation, either version 3 of the
   ** License, or (at your option) any later version.
   ```
   AGPL 的传染性会要求整个阅读器开源。

2. **它是位图级重排，不是文字重排**。流程是「页面光栅化 → 像素投影切行 → 切词 → 把词位图按目标宽度重新贴图」，产出的是图像而非可选可搜的文字流。关键函数：`k2pdfopt_reflow_bmp`（入口）、`bmpregion_find_textrows`（行检测）、`wrapbmp_add`（按宽重排）。

另有 C/C++ 原生依赖，与「绿色单文件 exe」冲突。

**来源**：[koptreflow.c](https://raw.githubusercontent.com/koreader/libk2pdfopt/master/lib/koptreflow.c)（入口与许可头均已核验）

### 1.2 pdf.js 没有重排能力，但提供了原料

在 pdf.js 仓库全文检索 `reflow`，**命中数为 0**。`text_layer.js` 的职责是把透明文字绝对定位盖在 canvas 上（供选择/复制/搜索），`struct_tree.js` 是 Tagged PDF 的无障碍语义树，都不是版面重排。

但 `getTextContent()` 返回的每个文本片段带齐了自研重排所需的字段：

```js
{
  str,        // 文本内容
  dir,        // 书写方向
  transform,  // 变换矩阵，含坐标与字号
  width,      // 宽度
  height,     // 高度
  fontName,   // 字体名
  hasEOL,     // 是否行尾
}
```

**来源**：[pdf.js text_layer.js](https://raw.githubusercontent.com/mozilla/pdf.js/master/src/display/text_layer.js)

### 1.3 纯 JS 重排的两个硬限制

| 限制 | 说明 |
| --- | --- |
| 只对**文本型** PDF 有效 | 扫描件无文本层，须先 OCR |
| **不能回写 PDF** | pdf-lib 官方 Limitations 原文（已核验）：不提供编辑表单域之外页面文字的 API |

**中文特有的坑**：k2pdfopt 的换行启发式基于「词间距」（`-ws`，以字母 o 的高度为单位）。中文没有空格，该启发式失效，需改为按字断行规则。

### 1.4 pdf-lib 能力边界

| 能力 | 支持 | 说明 |
| --- | --- | --- |
| 合并 / 拆分 / 删页 / 旋转 / 裁剪 | ✅ | 内置 API，各约 10–20 行 |
| 表单填写 | ✅ | 内置 |
| 水印 / 加页码 | ⚠️ | 无内置，用 `drawText` + `rotate` / `opacity` 手写 |
| **加密** | ❌ | README 原文（已核验）：*"pdf-lib does not currently support encrypted documents."* |

技术栈：纯 JS / TypeScript，零原生依赖（deps 仅 `pako`、`tslib`、`@pdf-lib/upng`、`@pdf-lib/standard-fonts`），MIT，`pdf-lib.esm.min.js` 约 511 KB。

**来源**：[pdf-lib README](https://raw.githubusercontent.com/Hopding/pdf-lib/master/README.md)

### 1.5 建议路线

1. **先做「适配宽度」阅读模式** —— 零新依赖，纯 CSS/Canvas 缩放裁剪。这正是 k2pdfopt `-mode fw` 的定位，其文档原文：*"without doing any text re-flow … best way to preserve the original layout"*。
2. **再做文字级重排** —— 基于 `getTextContent()` 自研：行聚类 → 列检测 → 段落合并 → HTML 重排。只做阅读层，不产出 PDF。先限定单栏/双栏正文，跳过表格与公式。
3. 扫描件重排放最后，依赖 OCR 就绪。

## 2. 中文 OCR（已定：RapidOCR）

### 2.1 两条路线的体积对比

| 方案 | 体积 | 中文精度 | 实现难度 |
| --- | --- | --- | --- |
| tesseract.js | 约 5–7 MB | 印刷体够用 | 低 |
| **RapidOCR（PP-OCR ONNX）+ onnxruntime-web** | **28–35 MB** | 更好 | 中（需自写前后处理） |

**tesseract.js 的体积细节**（供对比）：WASM 内核 2.73 MB + 中文语言包 1.64 MB(gz) + JS 0.2 MB。语言包用的是 `4.0.0_best_int` 整数化模型，**远小于上游 `tessdata` 标准版的 42.31 MB**——选错来源体积会差 25 倍。

### 2.2 RapidOCR 的体积构成

| 组件 | 体积 |
| --- | --- |
| `ch_PP-OCRv4_det_mobile.onnx` | 4.53 MB |
| `ch_PP-OCRv4_rec_mobile.onnx` | 10.35 MB |
| `ch_ppocr_mobile_v2.0_cls_mobile.onnx` | 0.56 MB |
| `onnxruntime-web` 的 `ort-wasm-simd-threaded.wasm` | 13.31 MB |
| 合计 | **约 28–32 MB** |

### 2.3 必须先排除的选项

| 方案 | 排除理由 |
| --- | --- |
| `onnxruntime-node` | win32 二进制单独 **131.78 MB**，整包 282.6 MB |
| `onnxruntime-web` 的 `jsep`(WebGPU) 变体 | 26.5 MB，体积翻倍且桌面无收益 |
| `onnxruntime-web` 的 `asyncify` 变体 | 24.6 MB，同上 |
| 上游 `tessdata` 标准版中文包 | 42.31 MB |
| `Scribe.js` | AGPL-3.0，仓库 343 MB |

### 2.4 落地要点

- 官方 [RapidOCR](https://github.com/RapidAI/RapidOCR) **没有 JS/WASM 版本**（仓库只有 `python/` 与 `assets/`），需自行用 `onnxruntime-web` 串起 det → cls → rec 三段，含 DB 后处理与 CTC 解码。
- 模型从 modelscope 下载后固化进包，保证纯离线。
- 需 OCR 的 PDF 页面先用 `pdfjs-dist` 渲染成图，再喂模型。

### 2.5 未验证项

**Tesseract 与 PaddleOCR 的中文精度对比没有权威横向基准**，只有社区普遍反馈「PaddleOCR 更准」（中等置信度）。落地前建议用真实样张实测。

## 3. 本地词典（已定：js-mdict@6.x）

### 3.1 许可风险是首要问题

`js-mdict` 在 **2026-03-20 的 v7.0.0** 从 MIT 转为 **AGPL-3.0**。README 原文（已核验）：

> As of **March 20, 2026**, `js-mdict` has transitioned from the MIT License to the **GNU AGPL-3.0**.
> **Legacy Versions**: All versions prior to v7.0.0 remain under the MIT License.

**决策：锁定 `js-mdict@6.x`（MIT）。** 备选是 `mdict-js`（MIT，2022 年后停更）。

### 3.2 能力与限制

| 项 | 值 |
| --- | --- |
| 解析器体积 | 0.43 MB（对绿色 exe 几乎无影响） |
| 查词性能 | `lookup` 约 2 万次/秒 |
| 依赖 | 仅 `commander` + `levenshtein-edit-distance`，但用到 Node `zlib`，**须在主进程跑** |

**支持的检索方式**：精确 `lookup`、前缀 `prefix`、子串 `contains`、编辑距离 `fuzzy_search`、关联词 `associate`、拼写建议 `suggest`。

**关键限制**：`contains()` 搜的是**词条 key，不是释义正文**。MDX 是「索引 + 压缩块」结构，没有倒排索引，**做不了释义全文检索**。要全文需自建索引，代价高，不建议。

### 3.3 词典文件的分发

- **词典文件不打进 exe**，由用户自行导入 `.mdx`，体积代价趋近于零。
- **商业词典（牛津、朗文、柯林斯等）受版权保护，不可随产品分发。**
- 可合法内置的免费词典：CC-CEDICT（汉英，CC BY-SA 4.0）。

## 4. 简繁转换

**选定 `opencc-js`。** README 原文（已核验）：*「纯 JavaScript 实现……不需要 native binary，也不会在运行时下载字典文件」*，对比表中「需要 native binary」一栏为 ❌。

实测打包产物（jsDelivr 元数据核验）：

| 方向 | 体积 |
| --- | --- |
| 繁 → 简 | **106.5 KiB** |
| 简 → 繁 | 1.05 MB |
| 双向全功能 | 1.14 MB |

纯 ESM，可直接跑渲染进程，接进 Vite 零成本。

**排除项**：`opencc-wasm`（23.67 MB，性价比差）、npm `opencc`（原生绑定 3.45 MB，破坏绿色单文件）。

**精度说明**：官方声明转换流程已对齐 upstream OpenCC 并通过 golden 测试，但「不保证对所有输入完全一致」；不支持 jieba 等扩展分词。对阅读器场景足够。

## 5. 漫画压缩包

### 5.1 格式映射

CBZ = ZIP、CBR = RAR、CB7 = 7z、CBT = TAR。依据 [Calibre 源码](https://raw.githubusercontent.com/kovidgoyal/calibre/master/src/calibre/__init__.py) 的按 magic bytes 分派逻辑（`Rar` → unrar，`PK` → zip，`7z` → seven_zip）。

### 5.2 各格式的实现代价

| 格式 | 方案 | 体积 | 备注 |
| --- | --- | --- | --- |
| CBZ（zip） | **项目已依赖 `jszip`** | 0 | 直接可用 |
| CBT（tar） | `tar-stream`（MIT，34 KB） | +34 KB | Node 无内置 tar 解析 |
| CB7（7z） | `libarchive.js` | +1 MB | 见下 |
| CBR（rar） | `libarchive.js` | 同上 | 见下 |

**推荐路径**：先只做 CBZ（零新依赖），再引入 **`libarchive.js@2.0.2`（MIT）** 一次性覆盖 CBT/CB7/CBR。

libarchive 自带的 RAR 读取器是 **BSD-2-Clause 实现，与 unRAR 无版权关系**（`archive_read_support_format_rar.c` / `rar5.c`），支持 RAR4 与 RAR5。

**已知局限**（源码注释）：不支持 QuickOpen、恢复记录、未知解压尺寸、加密 RAR。对漫画包（通常是普通压缩的图片）影响极小。

**走 unRAR 路线的许可义务**（如改用 `7z-wasm`）：unRAR 许可要求随包分发时必须在文档中显著声明，且**不得用于开发 RAR 兼容压缩器**。

### 5.3 图片排序规则（照 Calibre）

只收录 `png/jpg/jpeg/gif/webp`，按自然序（`numeric_sort_key`）排列，忽略 `__MACOSX/`。

## 6. 跨文档全文检索

### 6.1 现状复核（本机实测）

| 项 | 结果 |
| --- | --- |
| `sqlite_version` | 3.45.2 |
| FTS3 | **可用** ✓ |
| FTS4 | **可用** ✓ |
| FTS5 | 不可用（`no such module: fts5`） |
| wasm 字节扫描 | 含 `ENABLE_FTS3`，不含 `ENABLE_FTS5` |

上游 `sql-js/sql.js` 的 `Makefile` 编译开关确实只有 `SQLITE_ENABLE_FTS3` / `SQLITE_ENABLE_FTS3_PARENTHESIS`，没有 `SQLITE_ENABLE_FTS5`；启用 FTS5 的 PR #594 至今未合并。

**因此全文检索有三条路，FTS5 不是必须的。**

### 6.2 路线对比

| 路线 | 做法 | 改动量 | 体积 | 评价 |
| --- | --- | --- | --- | --- |
| **A. 现有 FTS4 + bigram 预处理** | 中文入库前切成 2 字片段再建索引 | 低（只加索引与查询方法，不换驱动） | 索引约 2× 原文 | **推荐先做** |
| B. 换 `node-sqlite3-wasm` | MIT、WASM、sqlite 3.53.4、含 FTS5、直接读写文件 | 中（改 `db.service.ts` 的 API 调用方式） | — | 需要真 FTS5 时再上 |
| C. `flexsearch` + `Charset.CJK` | 纯 JS 索引库，中文子串开箱可用 | 中（需自己维护 doc→book 映射与落盘） | 51 KB | 只要「一个搜索框」时可选 |

**FTS4 的中文问题**：内置分词器对 CJK 无效（整段连续汉字被当作单个词元），所以**必须自己做 bigram 预处理**。

**bigram 方案实测数据**（2000 篇 / 25.7 万字）：建索引 111 ms，查询 2 ms，导出 2.2 MB，重载后可查。

**已知代价**：索引体积约为原文 2 倍；`snippet()` 返回的是 bigram 词流（形如 `" 这是 是一 一本 中[中文]…"`），**高亮需回原文自行定位**。

**FTS5 的坑（若走路线 B）**：SQLite 内置的 `tokenize='trigram'` 才是中文子串检索的正解（无需分词器），但**查询串短于 3 字符时无法命中**。中文双字词极常见，因此需 trigram 列 + bigram 列双索引，或对 <3 字查询回退 `LIKE`。

### 6.3 可复用的现有资产

项目已有正文抽取链路可直接复用，无需新写解析器：`extractBookSections`（`electron/ipc/index.ts`）与 `splitText`（`electron/services/rag.ts`）。

## 7. 体积总账

| 模块 | 体积 |
| --- | --- |
| 简繁转换 `opencc-js`（繁→简） | +0.1 MB |
