## 第一部分 · 产品定义

### 1. 产品定位

**纯离线、本地优先、学习向 + 精读向的专业级本地阅读器。**

所有文档解析、渲染、检索、存储均在本机完成，不依赖任何外部服务。

对标对象：Koodo Reader、Calibre、系统自带阅读器、各类小说 App。

核心差异化补齐四个短板：

| 短板（市面现状） | 本产品对策 |
| --- | --- |
| 依赖联网、隐私不可控 | 100% 纯离线，文件与笔记不出本机 |
| 功能简陋，只能看不能管 | 本地书库管理 + 批注笔记体系化 |
| 学习/精读能力薄弱 | 生词本、词典、TTS、笔记知识库 |
| PDF 阅读体验差 | PDF 重排、裁剪、批注、渲染选项 |

### 2. 离线优先原则与例外能力

**产品默认运行形态为纯离线**：断网环境下全部核心功能可用；文档解析、渲染、检索、存储全部在本机完成，不需要任何外部服务。

**例外能力（保留，默认关闭）**：代码中已实现的 AI 阅读助手、本地大模型推理、离线 OCR、语义检索，作为**附加能力保留**，不纳入产品主线，也不删除、不隐藏入口：

- 默认关闭，需用户在设置中显式开启后才生效
- 未开启时不发起任何网络请求，不因联网能力缺失而功能降级
- 开启前向用户明示会产生网络访问

**已于 2026-09-17 移除**：在线书源（书源管理 / 在线阅读 / 追更订阅 / 文本净化规则）与 WebDAV 云端同步整条链路已从代码中删除，不再是本产品的保留能力。云端备份由本地备份 + 快照回退替代；在线阅读由本地文件导入替代。原「附加能力总开关」保留，现只守模型的下载与 AI 助手、语义检索的外接服务两类出站点。

**明确不做**

- 在线协作、多人批注、网页剪藏（协作必然联网，与纯离线定位冲突）
- 生物识别解锁（Electron 的 `promptTouchID` 标注 `@platform darwin`，Windows 无内置接口，需引入原生模块，会破坏绿色单 exe 前提）
- 界面多语言切换（中文个人阅读器，需要抽取全部文案并改造十余个组件，收益与工程量不成比例）
- 上传任何本地文件到第三方服务器
- 任何形式的遥测、埋点、使用数据上报
- 检查更新与自动更新的网络版本检查（版本信息以「关于软件」静态展示为准）

### 3. 优先级定义

| 级别 | 定义 |
| --- | --- |
| P0 | 核心必做，V1.0 必须实现，产品可用底线 |
| P1 | 重要体验，V1.1 迭代，对标 Koodo 基础体验 |
| P2 | 扩展增强，V2.0 可选开发，丰富使用场景 |
| P3 | 增值特色，V3.0 后期可选，开发成本较高 |

### 4. 功能分层模型

整套功能由浅入深，构成完整金字塔：

| 层级 | 内容 | 作用 |
| --- | --- | --- |
| 底层 | 稳定性、容错、性能、数据安全（防抖、增量备份、快照、防误触） | 专业软件与玩具软件的分界线 |
| 中层 | 阅读体验、格式兼容、排版优化、沉浸式阅读 | 用户感知最强、留存最高 |
| 高层 | 批注笔记知识库、学习能力、词典、TTS、阅读数据 | 从「工具」升级为「知识库」 |
| 顶层 | 个性化自定义、本地智能算法、插件生态 | 远期壁垒 |

### 5. 与现有实现的关系（已裁决：保留，默认关闭；书源族与 WebDAV 另行裁决为移除）

现有代码已实现 **AI 阅读助手（摘要 / 问答 / 翻译 / 思维导图 / 语义检索）**、**本地大模型下载与进程内推理**、**离线 OCR**。

**裁决结果：保留**，不删除、不隐藏入口；但归入第 40 章的「附加能力」，默认关闭，不计入纯离线主线。产品对外定位仍为纯离线阅读器。

**另一条裁决（2026-09-17）**：在线书源与 WebDAV 同步**不保留，已删除**。理由：这两项的能力本身完全架在联网之上——书源的价值全在「有源可抓」，WebDAV 的价值全在「有远端可同步」，它们没有离线形态可退；而 AI 与模型下载即使外接服务不可用，仍能退回本机模型推理，属「可离线的能力」，性质不同。删除范围与替代路径见第 40 章。

### 19. 模块十四 · 文档编辑与画布标注

> **本模块不在路线图（2026-09-18 裁决）。**

规划过 8 条，均未实现，也不计划实现：撤销 / 恢复操作、直接编辑 PDF 文字、修改 / 替换图片、插入文字与图片、插入形状与箭头、添加文本框、手写涂鸦、画布式高亮。（文本级高亮另有实现，见模块四。）

**判定依据**：逐关键词回代码核实，本模块**零代码、零依赖**——`撤销` 只出现在 confirm 文案里，`redo` 只是跳转历史的「前进」图标，`drawText` 只在 `pdf-edit.ts` 的水印与页码（固定内容盖章，不是可编辑插入），`文本框` 只在 OCR 的行框识别里，`插入形状` / `箭头` / `手写` / `涂鸦` / `替换图片` 等全部零命中；依赖侧也没有相关库（`tldraw` / `fabric` / `konva` / `signature_pad` / `perfect-freehand` 全库零命中）。

一个易误判点：`Reader.tsx` 里确实有 `<canvas>`，但那是 pdfjs 的页面渲染画布（另有导出缩略图、导出当前页图片两个用途），**不是可编辑画布**，与本模块无关。

**为什么直接判死**：这几条全是重型编辑能力（PDF 内容编辑、矢量标注、手写），与本项目「书库文件只读、改动一律落数据库」的设计模型直接冲突——真要做等于换一个产品形态，不是排期问题。若将来重启，须先回答一个产品问题：**编辑产物是写回源文件，还是另存副本**？

### 38. 风险与优化方向

**风险**

1. 功能过多，需做好分级，默认简洁、进阶可开，避免新手 UI 臃肿。
2. 本地数据持续增长，需优化数据库读写性能。
3. 自定义项过多，需提供「默认最优配置」，降低学习成本。

**优化方向**

1. 增加「新手模式 / 专业模式」双 UI。
2. 高级功能默认隐藏，手动开启。
3. 严格按 V3.1 → V3.2 → V4 节奏迭代，不堆砌开发。
