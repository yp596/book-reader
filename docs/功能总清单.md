## 第一部分 · 产品定义

### 1. 产品定位

**纯离线、本地优先、学习向 + 精读向的专业级本地阅读器。**

所有文档解析、渲染、检索、存储均在本机完成，不依赖任何外部服务。

对标对象：Koodo Reader、Calibre、系统自带阅读器、各类小说 App。

核心差异化补齐四个短板：

| 短板（市面现状） | 本产品对策 |
| --- | --- |
| 依赖联网、隐私不可控 | 100% 纯离线，文件与笔记不出本机 |
| 功能简陋，只能看不能管 | 本地书库管理 + 批注笔记体系化 |
| 学习/精读能力薄弱 | 生词本、词典、TTS、笔记知识库 |
| PDF 阅读体验差 | PDF 重排、裁剪、批注、渲染选项 |

### 2. 离线优先原则与例外能力

**产品默认运行形态为纯离线**：断网环境下全部核心功能可用；文档解析、渲染、检索、存储全部在本机完成，不需要任何外部服务。

**例外能力（保留，默认关闭）**：代码中已实现的 AI 阅读助手、本地大模型推理、在线书源与在线阅读、WebDAV 同步，均作为**附加能力保留**，不纳入产品主线，也不删除、不隐藏入口：

- 默认关闭，需用户在设置中显式开启后才生效
- 未开启时不发起任何网络请求，不因联网能力缺失而功能降级
- 开启前向用户明示会产生网络访问

**明确不做**

- 在线协作、多人批注、网页剪藏（协作必然联网，与纯离线定位冲突）
- 生物识别解锁（Electron 的 `promptTouchID` 标注 `@platform darwin`，Windows 无内置接口，需引入原生模块，会破坏绿色单 exe 前提）
- 界面多语言切换（中文个人阅读器，需要抽取全部文案并改造十余个组件，收益与工程量不成比例）
- 上传任何本地文件到第三方服务器
- 任何形式的遥测、埋点、使用数据上报
- 检查更新与自动更新的网络版本检查（版本信息以「关于软件」静态展示为准）

### 3. 优先级定义

| 级别 | 定义 |
| --- | --- |
| P0 | 核心必做，V1.0 必须实现，产品可用底线 |
| P1 | 重要体验，V1.1 迭代，对标 Koodo 基础体验 |
| P2 | 扩展增强，V2.0 可选开发，丰富使用场景 |
| P3 | 增值特色，V3.0 后期可选，开发成本较高 |

### 4. 功能分层模型

整套功能由浅入深，构成完整金字塔：

| 层级 | 内容 | 作用 |
| --- | --- | --- |
| 底层 | 稳定性、容错、性能、数据安全（防抖、增量备份、快照、防误触） | 专业软件与玩具软件的分界线 |
| 中层 | 阅读体验、格式兼容、排版优化、沉浸式阅读 | 用户感知最强、留存最高 |
| 高层 | 批注笔记知识库、学习能力、词典、TTS、阅读数据 | 从「工具」升级为「知识库」 |
| 顶层 | 个性化自定义、本地智能算法、插件生态 | 远期壁垒 |

### 5. 与现有实现的关系（已裁决：保留，默认关闭）

现有代码已实现 **WebDAV 云端同步**、**在线书源与在线阅读**、**AI 阅读助手（摘要 / 问答 / 翻译 / 思维导图 / 语义检索）**、**本地大模型下载与进程内推理**。

**裁决结果：全部保留**，不删除、不隐藏入口；但归入第 40 章的「附加能力」，默认关闭，不计入纯离线主线。产品对外定位仍为纯离线阅读器。

### 38. 风险与优化方向

**风险**

1. 功能过多，需做好分级，默认简洁、进阶可开，避免新手 UI 臃肿。
2. 本地数据持续增长，需优化数据库读写性能。
3. 自定义项过多，需提供「默认最优配置」，降低学习成本。

**优化方向**

1. 增加「新手模式 / 专业模式」双 UI。
2. 高级功能默认隐藏，手动开启。
3. 严格按 V3.1 → V3.2 → V4 节奏迭代，不堆砌开发。

### 41. 开放问题与依赖

1. **TXT 关键字 / 正则目录解析的默认规则集**：可移植的现成方案与落地顺序见 [目录识别方案.md](./目录识别方案.md)。
2. **朗读（TTS）已实现，不再是「选型」问题**：走 Web Speech API（`speechSynthesis` + `SpeechSynthesisUtterance`，见 `Reader.tsx`），音色取自系统本地语音（中文按 `v.lang.startsWith('zh')` 选），支持变速、按页朗读与朗读选中，单次上限 15000 字。因为不随包带语音引擎，原「跨平台语音包体积」的顾虑不再成立。**待确认（未验证）**：`getVoices()` 用 `.find()` 取第一个中文音色，部分平台的 Chromium 可能同时提供网络音色——断网验收时需确认选中的是本地音色。
3. **本地 OCR 已实现**（2026-09-11 接通），且未采用 Tesseract：`src/utils/ocr/` 为随包模型 + 自研 CTC 解码与后处理（`engine.ts` / `ctc.ts` / `db-postprocess.ts`），扫描版 PDF 与漫画可对当前页取字、结果可复制，全程本机运算。原「Tesseract 安装包与依赖体积评估」不再适用。
4. **书库加密方案**：本地数据库加密需技术评估选型。
5. **PDF 批注能力**：PDF 无 CFI/字符偏移定位体系，检索、划词、书签、高亮需另建坐标方案才能补齐。
6. **PDF 重排算法**：需确定用文本层重排还是版式分析，扫描件需配合 OCR，工作量差异极大。
7. **生词释义数据源**：Pro 释义若要离线，需引入本地词典数据文件，体积与授权需评估。
8. **附加能力开关粒度**：AI / 在线书源 / WebDAV 设一个总开关还是按能力分开关，需明确。
9. **离线可验证性**：需在验收环节加入断网测试，确认未开启附加能力时无任何出站请求、无功能降级。
10. **剩余高难度功能的依赖选型**（PDF 重排与编辑、本地词典、简繁转换、跨文档全文检索）：方案、体积代价与已定决策见 [依赖选型调研.md](./依赖选型调研.md)。（原列表中的**中文 OCR** 与**漫画压缩包**均已落地，见第 3 条与模块八，已从待选型中移除。）
